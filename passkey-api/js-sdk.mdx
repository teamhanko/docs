`@teamhanko/passkeys-sdk` is a typed API client for JavaScript runtimes with `fetch`, including Node.js, Bun, and Deno. This guide focuses on backend usage: keep the secret API key out of browser bundles.

For the complete browser/backend flow, start with [Register and sign in with passkeys](/passkey-api/example-implementation). The SDK replaces HTTP calls to the Passkey API; your application still owns authentication policy, session handling, CSRF protection, and result verification.

## Install and configure

<CodeGroup>
```bash npm
npm install @teamhanko/passkeys-sdk
```
```bash yarn
yarn add @teamhanko/passkeys-sdk
```
```bash pnpm
pnpm add @teamhanko/passkeys-sdk
```
```bash bun
bun add @teamhanko/passkeys-sdk
```
</CodeGroup>

Get your tenant ID and secret API key from [your Passkey API project](/passkey-api/setup-passkey-project). Store both in your backend environment:

```bash .env
PASSKEYS_TENANT_ID=your-tenant-id
PASSKEYS_API_KEY=your-secret-api-key
```

```ts
import { tenant } from "@teamhanko/passkeys-sdk";

const tenantId = process.env.PASSKEYS_TENANT_ID;
const apiKey = process.env.PASSKEYS_API_KEY;
if (!tenantId || !apiKey) {
  throw new Error("Missing Passkey API configuration");
}

const passkeyApi = tenant({ tenantId, apiKey });
```

Load these environment variables using your deployment platform or environment loader. For self-hosting, supply `baseUrl`, for example `tenant({ tenantId, apiKey, baseUrl: "https://passkeys.example.com" })`. The client appends the tenant path; do not include the tenant ID in `baseUrl`.

Create or select the client from trusted application configuration. The tenant identifies your Passkey API project; the user ID identifies an existing user in your application. For operations on a signed-in user, derive that ID from server-side authentication state.

## SDK calls and API routes

| SDK call | API route | Result |
| --- | --- | --- |
| `registration.initialize({ userId, username })` | `/registration/initialize` | WebAuthn creation options |
| `registration.finalize(credential)` | `/registration/finalize` | `{ token }` |
| `login.initialize()` | `/login/initialize` | WebAuthn request options |
| `login.finalize(assertion)` | `/login/finalize` | `{ token }` |
| `user(userId).credentials()` | `GET /credentials?user_id=...` | Credential list |
| `credential(credentialId).remove()` | `DELETE /credentials/{credential_id}` | No response body |
| `jwks()` | `GET /.well-known/jwks.json` | Public signing keys |

The SDK unwraps successful API responses and throws on API errors. Creation and request options include `publicKey`; finalization returns an object containing the token, not a decoded user or an application session.

## Register a passkey

After authorizing enrollment for the authenticated user, initialize registration:

```ts
const creationOptions = await passkeyApi.registration.initialize({
  userId: authenticatedUser.id,
  username: authenticatedUser.email,
  displayName: authenticatedUser.displayName,
});
```

Store the challenge and expected user against the enrollment session before returning `creationOptions` to the browser. The browser performs WebAuthn `create()` and returns the serialized credential response to your backend. Match it to the pending enrollment, then submit that same response:

```ts
const result = await passkeyApi.registration.finalize(credential);
```

Complete the pending enrollment only after API verification succeeds. The browser ceremony and HTTP forwarding are demonstrated in the [integration guide](/passkey-api/example-implementation). The SDK does not itself bind enrollment to your application's current session.

## Sign in with a passkey

The following snippets use the [application-defined session helpers](/passkey-api/login-session-binding#backend-integration-helpers). Implement them in your backend; they are not exported by the SDK.

At the start of login:

```ts
const loginOptions = await passkeyApi.login.initialize();
await rememberLogin(req, loginOptions.publicKey.challenge, "login");
// Return loginOptions to the browser after the pending attempt is stored.
```

The browser performs WebAuthn `get()` and returns the assertion. Complete login on your backend:

```ts
const result = await passkeyApi.login.finalize(assertion);
const userId = await acceptLogin(req, result.token, "login");
await establishSession(req, res, userId);
```

`acceptLogin` must verify the result token and atomically consume a matching pending attempt before a full application session is created. Follow [Login session binding](/passkey-api/login-session-binding) for the required checks and deployment compatibility. Calling `finalize()` alone does not perform these application checks.

The current SDK's `login.initialize()` has no user-ID argument and starts discoverable login. The API also supports login with `user_id`, which requires a secret API key; use a backend HTTP call for that variant. See [Start Login](/passkey-api/reference/start-login).

## MFA

Use the user's MFA methods after your existing first-factor check succeeds. [Passkeys and MFA](/passkey-api/mfa) explains how the routes differ, authenticator defaults, and the complete second-factor flow.

For MFA credential enrollment, from an authenticated enrollment session:

```ts
const options = await passkeyApi.user(authenticatedUser.id)
  .mfa.registration.initialize({ username: authenticatedUser.email });
// Bind options.publicKey.challenge to enrollment; send options to the browser.
// After matching the browser response to that pending enrollment:
const result = await passkeyApi.user(authenticatedUser.id)
  .mfa.registration.finalize(credential);
```

For login, derive `expectedUserId` from trusted first-factor session state. At initialization:

```ts
const loginOptions = await passkeyApi.user(expectedUserId).mfa.login.initialize();
await rememberLogin(req, loginOptions.publicKey.challenge, "mfa", expectedUserId);
// Return loginOptions to the browser.
```

After the browser returns its assertion:

```ts
const result = await passkeyApi.user(expectedUserId).mfa.login.finalize(assertion);
const userId = await acceptLogin(req, result.token, "mfa");
await establishSession(req, res, userId);
```

The SDK's `.user(userId)` supplies the user ID during initialization. Finalization sends the credential response; it does not add a separate expected-user check. Your session helper must reject a result for any other user and consume the pending attempt before granting full access.

## Manage credentials

```ts
const credentials = await passkeyApi.user(authenticatedUser.id).credentials();

// After your backend authorizes deletion of this credential for the user:
await passkeyApi.credential(credentialId).remove();
```

The tenant API key authorizes access at tenant scope. Verify ownership in your backend before accepting an end-user request to remove or change a credential.

The current SDK has no credential-update method. To rename a credential or change `is_mfa`, call [Update Credential](/passkey-api/reference/credentials/update-credential) over HTTP from your backend. The flag update requires the updated API release; changing TypeScript schema types alone does not add an SDK method. See [permitted credential usage](/passkey-api/mfa#change-a-credentials-permitted-usage) for the security implications.

## Handle errors

Wrap SDK calls in your application's error handling. Do not establish a session, mark MFA enrollment complete, or report success after an API failure.

```ts
try {
  const result = await passkeyApi.login.finalize(assertion);
  const userId = await acceptLogin(req, result.token, "login");
  await establishSession(req, res, userId);
} catch (error) {
  // Record appropriate diagnostic information on the backend.
  // Return a generic failure and require a new attempt where appropriate.
  res.status(401).json({ message: "Unable to complete sign-in" });
}
```

This is an integration sketch: `req`, `res`, assertions, authenticated-user state, and session helpers are supplied by your application. Configure CSRF protection and secure session storage before exposing the handlers.
