---
title: Finalize login from the browser
description: Finalize passkey authentication from the browser while binding the result to your application session.
---

The browser can call `/login/finalize` directly without a secret API key. Your backend must still associate the authentication result with the application session that initiated it.

## Recommended flow

1. The browser calls your backend to start login.
2. Your backend calls `/login/initialize`, stores `publicKey.challenge` in an expiring pending login for the current session, and returns the options.
3. The browser authenticates with a passkey and submits the assertion directly to `/login/finalize`.
4. The browser sends the returned `token` to your backend.
5. Your backend verifies the JWT, compares its signed `challenge` with the pending login for this session, and atomically consumes that record before creating a session for `sub`.

Follow [Bind login results to your session](/passkey-api/login-session-binding) for JWT validation, CSRF protection, expected-user checks, one-time completion, and deployment requirements.

The token identifies the user through `sub`; it does not contain a username. Use the configured tenant's `/{tenant_id}/.well-known/jwks.json` to verify its signature, and validate the audience and expiration. Signature validation alone does not bind the result to the current session.

## Existing browser-only initialization

The public initialization endpoint remains available. However, the challenge-claim flow requires your backend to store the expected challenge before authentication. An integration that first contacts its backend with a completed JWT cannot establish this binding merely by checking the token signature or storing a challenge supplied alongside that token.

Move initialization through your backend to adopt this flow. Finalization can remain a direct browser-to-API request. Never expose a secret API key in frontend code.
